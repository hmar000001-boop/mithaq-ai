# Release signing checklist

## Phase-0 GitHub Release signing

- Generate one long-lived Android signing keystore for both Mithaq packages.
- Store at least two offline backups in secure locations.
- Never upload the keystore to GitHub or include it in implementation ZIPs.
- Add GitHub Actions secrets listed in the root README.
- Confirm the same keystore signs both main and Network Companion release APKs.
- Verify signatures after each release with `apksigner verify --print-certs` and confirm certificate fingerprints match.
- Keep debug APKs clearly separated from release artifacts.
- Do not rotate the signing certificate after release without a planned supported signing-key upgrade.

## Google Play signing gate — mandatory before first rollout

The Binder service is protected by an Android `signature` permission. Consequently, the **installed app-signing certificates** for `com.mithaq.app` and `com.mithaq.network` must match. The AAB upload certificate alone does not establish that: Google Play uses the app-signing key to sign optimized APKs distributed to devices.

For two new Play listings:

1. Decide and document the app-signing key strategy before releasing either listing to open testing or production.
2. In Play Console, configure the second app to use the same app-signing key as the first, or provide a copy of that same app-signing key during setup. Google documents these choices for new apps before rollout to open testing or production.
3. Verify the fingerprints of APKs generated by Play for both listings during internal testing.
4. Treat cross-package Binder authorization as a separate runtime security-qualification gate. The routine CI pipeline intentionally has no emulator E2E/instrumentation suite; host-JVM tests and manifest audits do not prove the Android runtime permission check.

Do not confuse the **upload key** (used to authenticate an AAB upload) with the **app-signing key** (used by Play to sign APKs installed by users). The current Phase-0 workflow uses one GitHub Actions key for the GitHub APK assets and AAB signing as a bootstrap arrangement. Before production, review whether to split the AAB upload key from the app-signing key and update Gradle/CI accordingly. The GitHub direct-download APKs must still be signed with the same certificate as the APKs delivered by Play if cross-channel updates and signature-protected Binder access are expected.

Official reference: https://support.google.com/googleplay/android-developer/answer/9842756
